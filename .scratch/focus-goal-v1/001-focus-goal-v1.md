## Problem Statement

容易拖延的使用者往往有明確的願望，例如減脂、學習或完成論文，卻缺少能立即執行的下一步。他們需要自行估算期限、能力、可用時間與任務順序，最後還要手動輸入日曆；這些步驟讓原本模糊但可完成的目標更容易停留在想法階段。

使用者需要一個安靜、可掌控的手機工具，協助把目標轉成由自己確認的具體行動，並可選擇性加入手機系統日曆，而非以壓力、羞辱或強制限制來驅動行動。

## Solution

建立以繁體中文為預設語言的 React Native iOS／Android App「Focus Goal」。V1 提供完整的核心流程：建立目標、以可修改的 AI 對話釐清規劃條件、設定固定可用時段、生成有日期和時間的計畫、逐項選取任務，以及匯出所選任務至系統日曆。

AI 所有建議均為暫定內容：使用者可接受、編輯或拒絕建議的期限、程度、偏好、限制、不可安排時段、里程碑與每一項任務。當期限與可用時間不足時，App 會透明說明風險並提供調整方向；當使用者改動任務而造成可用時段衝突時，App 只提供備用時段供選擇，不會自行改排。

## User Stories

1. 作為容易拖延的使用者，我想建立一個以自然語言描述的目標，讓我能從想法開始規劃。
2. 作為使用者，我想在首頁看見已建立的目標，讓我能快速回到正在進行的規劃。
3. 作為第一次使用者，我想在空白首頁看到範例目標與建立引導，讓我知道 App 可以如何協助我。
4. 作為使用者，我想從首頁新增目標，讓我能規劃新的減脂、學習或寫作目標。
5. 作為使用者，我想編輯目標的名稱與描述，讓計畫始終反映我真正要完成的事情。
6. 作為使用者，我想以對話方式補充目標背景，讓 AI 不會只根據一句模糊描述做武斷假設。
7. 作為使用者，我想查看 AI 建議的完成日期，讓我能判斷期限是否合理。
8. 作為使用者，我想修改或拒絕建議的完成日期，讓期限由我而不是 AI 決定。
9. 作為使用者，我想填寫每天或每週可投入的時間，讓計畫能符合我的現實生活。
10. 作為使用者，我想表明目前程度，讓任務難度能從我現有能力開始。
11. 作為使用者，我想補充偏好、限制與不可安排時段，讓計畫不會忽略我的生活情境。
12. 作為使用者，我想隨時回看並修改上述規劃條件，讓 AI 建議不會變成不可變更的前提。
13. 作為使用者，我想設定每週固定可安排時段，讓任務可被排入我實際能做事的時段。
14. 作為使用者，我想為不同星期設定多個時段，讓平日與週末能有不同的規劃方式。
15. 作為使用者，我想將某一天設定為不安排，讓計畫尊重我的休息與既有承諾。
16. 作為使用者，我想修改與刪除可用時段，讓設定可隨生活變化調整。
17. 作為使用者，我想明確看到 V1 不會讀取既有系統日曆來避開活動，讓我理解規劃的界線。
18. 作為使用者，我想要求 AI 依據目標與條件產生行動計畫，讓我不必自行把大目標拆成任務。
19. 作為使用者，我想在生成期間看到清楚、平靜的 loading 狀態，讓我知道系統正在處理而不必猜測。
20. 作為使用者，我想在 AI 生成失敗時看到可行的重試與手動調整方式，讓一次失敗不會丟失我的輸入。
21. 作為使用者，我想在計畫中看到建議完成日期，讓我掌握整體時間目標。
22. 作為使用者，我想看到每週摘要或里程碑，讓我能了解計畫的推進節奏。
23. 作為使用者，我想看到完整任務清單，讓我能在匯出前檢閱每個行動。
24. 作為使用者，我想在每項任務中看到日期、開始時間、結束時間、時長與簡短說明，讓我能直接判斷是否可執行。
25. 作為使用者，我想修改任何 AI 產生的任務內容、日期、時間與時長，讓計畫保有我的主控權。
26. 作為使用者，我想在可用時間不足以趕上期限時得到清楚提示，讓我不會誤以為計畫必定可行。
27. 作為使用者，我想看到延後期限、增加可用時段、降低範圍等調整建議，讓我能自行選擇合適的取捨。
28. 作為使用者，我想在修改任務至不符合可用時段時收到衝突提示，讓我能做出知情的安排。
29. 作為使用者，我想看到數個符合設定的備用時段，讓我可自行決定是否將任務改到其中一個時段。
30. 作為使用者，我想保留自己輸入的衝突時間，直到我明確選擇替代時段或取消修改，讓 App 不會擅自改動我的計畫。
31. 作為使用者，我想逐項勾選要加入系統日曆的任務，讓我不必一次確認整份計畫。
32. 作為使用者，我想一鍵全選或取消全選任務，讓我能高效率管理大量任務。
33. 作為使用者，我想清楚看見目前已選取的任務數量，讓我知道將會匯出的內容。
34. 作為使用者，我想在未選取任務時得到合適引導，讓我知道需至少選擇一項才能加入日曆。
35. 作為使用者，我想在第一次匯出時被請求日曆權限，讓我能知情地授權。
36. 作為使用者，我想在權限被拒絕時看到清楚的原因與前往系統設定的可行指示，讓我仍能完成後續操作。
37. 作為使用者，我想把已選任務建立到手機系統日曆，讓具體行動能出現在我平常使用的行程工具中。
38. 作為使用者，我想在部分或全部日曆建立失敗時看到哪些任務失敗及可重試選項，讓我不會以為所有任務均已加入。
39. 作為使用者，我想在成功匯出後看到明確結果，讓我能安心開始執行。
40. 作為使用者，我想在設定頁查看日曆權限狀態，讓我能預先處理授權問題。
41. 作為使用者，我想在設定頁重新檢查或開啟系統權限設定，讓我能在拒絕後自行恢復功能。
42. 作為使用者，我想讓目標、可用時段、AI 計畫、任務變更與勾選狀態留存在手機本機，讓我重新開啟 App 時不會遺失進度。
43. 作為使用者，我想在 App 重開後繼續檢視與編輯未完成計畫，讓規劃可以長期使用。
44. 作為使用者，我想預設看到繁體中文及平靜、有行動感的文案，讓規劃過程不增加焦慮。
45. 作為使用者，我不想受到羞辱、懲罰或過度激進的文案，讓我能以可持續的方式完成目標。
46. 作為開發者，我想透過可替換的 AI 服務層提供 mock 回覆，讓核心流程能在未設定 AI 供應商憑證時展示與測試。
47. 作為開發者，我想讓日曆整合被封裝在跨平台介面後方，讓 iOS 與 Android 的權限差異不會滲入畫面與規劃邏輯。

## Implementation Decisions

- 採用 React Native 與 TypeScript 建立單一跨平台 App，目標平台為 iOS 與 Android。
- App 的 V1 畫面為：目標列表首頁、建立目標／AI 對話、可用時段設定、AI 計畫預覽、任務勾選與加入系統日曆、基本設定／權限狀態。
- 領域模型以 `Goal`、`PlanningContext`、`AvailabilityWindow`、`Plan`、`Milestone`、`Task`、`TaskSelection` 與 `CalendarExportResult` 為核心。每一項 AI 產出保存其可編輯欄位，而非只保存不可變的 AI 文本。
- `PlanningContext` 至少包括截止日期、可投入時間、目前程度、偏好、限制與不可安排時段；所有欄位可為空、可修改或可拒絕，不能被視為 AI 的固定前提。
- 可用時段以星期與本地時間區間表示；星期日無時段即代表不安排。V1 僅以使用者設定的時段進行可行性評估，不讀取或同步既有系統日曆。
- 規劃流程由單一高階 `PlanningWorkflow` seam 協調：驗證輸入、呼叫 AI 規劃服務、檢驗產生任務與可用時段／期限的可行性、產生不足警示，並輸出可供 UI 編輯的計畫。畫面只呼叫此工作流，不直接依賴特定 AI 供應商。
- AI 存取透過可替換的規劃服務介面封裝。開發預設提供確定性的 mock 實作，使用範例目標產生足以展示對話、里程碑、任務與時間不足警示的資料；日後可在不改變 UI 與領域模型下替換為正式 AI 供應商。
- 使用清楚的應用程式狀態管理分層：持久化的領域資料與短暫 UI 狀態分離。修改任務、勾選任務與匯出結果應立即反映，並在適當時機寫入本機儲存。
- 目標、規劃條件、可用時段、計畫、使用者編輯後的任務與勾選狀態均儲存在裝置本機；資料讀取、遷移與寫入錯誤必須顯示可理解的復原提示。
- 使用成熟的 React Native 跨平台日曆套件；以日曆閘道介面處理授權狀態、請求權限、開啟系統設定與建立事件。平台差異限制由閘道轉為一致的成功、部分失敗、拒絕與無法使用結果。
- 只有使用者勾選的任務才可建立系統日曆事件；事件包含任務名稱、開始及結束時間、時長與簡短說明。V1 不要求匯入、更新或刪除 App 以外的既有日曆事件。
- 任務編輯後若與可用時段衝突，保留使用者編輯值並顯示數個候選備用時段。只有使用者選擇候選時段時才套用改動；不得自動重新排程。
- 規劃預覽須獨立呈現完成日期、里程碑／每週摘要、任務明細與可行性警示。每個 AI 內容都具有明確的編輯入口。
- 採用安靜、簡潔、有行動感的繁體中文介面文案；避免使用羞辱、恐嚇、懲罰、連勝壓力或過度承諾式語言。
- 必須提供合理空白、載入、錯誤與成功狀態，以及可直接體驗流程的範例資料。

## Testing Decisions

- 好的測試應驗證使用者可觀察到的行為與領域輸出，例如計畫內容、警示、任務選取、權限處理與日曆匯出結果；不測試元件內部 state、hooks 呼叫順序或套件實作細節。
- 以 `PlanningWorkflow` 為最高且主要的測試 seam。使用 mock AI 服務和記憶體儲存／日曆閘道，測試不同規劃條件下的計畫生成、時間不足提示、任務可編輯性及衝突時不自動改排的行為。這是新專案唯一必要的核心服務 seam。
- 以整合／互動測試覆蓋完整路徑：建立目標、補充或修改條件、設定時段、生成計畫、選取任務、授權、匯出及重開後還原狀態。
- 日曆閘道以契約測試覆蓋授權已給予、首次允許、拒絕、受限制、單筆失敗及部分成功，使 UI 在兩平台上都得到一致可預期的結果。
- 持久化層以行為測試確認目標、時段、計畫、任務編輯與選取狀態可寫入並還原，以及損毀或讀取失敗時會顯示安全的錯誤／復原狀態。
- UI 測試覆蓋首頁空白與範例資料、生成 loading、AI 失敗、未選任務、權限拒絕、匯出成功與部分失敗等狀態；測試應使用可存取的文字與使用者操作，而不是視圖階層細節。
- 專案目前沒有可沿用的測試 prior art；建立後以此規格中的工作流與閘道契約測試作為基準。

## Out of Scope

- 推播提醒、連續追問、習慣打卡或任何督促機制。
- 娛樂 App 偵測、使用時間追蹤、封鎖或限制功能。
- 社群、排行榜、分享、協作或教練功能。
- 付款、訂閱、帳戶、雲端同步、跨裝置同步與後端服務。
- 讀取既有系統日曆並自動避開行程。
- 未經使用者同意的自動重新排程。
- 匯入、修改或刪除使用者既有的日曆事件。
- 正式 AI 供應商的憑證、計費與後端代理實作；V1 原型以可替換服務和 mock 回覆支援展示與測試。
- 除繁體中文預設介面外的完整國際化。

## Further Notes

- 成功指標以「使用者將可執行任務匯出至日曆」及「使用者能在不失去主控權下持續回到既有計畫」為主；V1 不應承諾或量測娛樂限制效果。
- 「30 天減脂 5 公斤」、「兩週學完 Python 基礎」及「完成畢業論文第一章」應提供為可重複使用的範例資料，涵蓋不同期限、程度與時段設定。
- 日曆 API 的實際授權字串、可選日曆帳戶與系統設定深連結將因平台與選定套件而異，實作時需以真機驗證；對使用者一律呈現可行的下一步。
- 此規格預設日曆事件以使用者裝置目前時區建立，並應在同一計畫顯示一致的本地日期與時間。
