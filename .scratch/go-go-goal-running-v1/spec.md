## Problem Statement

想養成跑步習慣的人通常知道運動有益，卻很容易把「今天要跑」延後、忽略，最後放棄整個目標。一般待辦清單只會記錄任務是否完成，無法讓使用者面對缺席，也不會建立一份可長期回顧的承諾紀錄。

使用者需要一個名為 Go Go Goal 的私人行動 App：先協助他訂出安全且合理的跑步計畫，經過明確承諾後，以當天兩張、相隔至少 15 分鐘的相片完成自我打卡；在缺席時用嚴肅但不羞辱的方式要求回應，並保留完成、暫停、放棄及缺席的歷史。

## Solution

將目前通用的目標規劃原型轉為 Go Go Goal V1，聚焦首頁的 Keep Fit 類別及其中唯一可用的 Running 方式。使用者先登入並進入私人 Workspace，透過 Gemini Flash 協助完成安全篩查和可修改的計畫草案；只有按下「我承諾這個計畫」才會建立正式目標。

已承諾的 Running 目標在每個預定跑步日只要求日期、沒有固定開跑時間。使用者在同一曆日上傳兩張相片，兩者間隔至少 15 分鐘，即完成當天打卡。App 在 10:00 與 20:00 推播提醒，午夜仍未完成即標記為缺席，翌日要求使用者補救或說明。Workspace 及日曆保留可回顧的文字紀錄；原始相片保存 90 天後刪除。

Gemini 只提供計畫草案與正向、簡短的相片鼓勵。所有承諾、時間、缺席、保存及完成規則都由後端的確定性邏輯執行。

## User Stories

1. 作為新使用者，我想先登入 Go Go Goal，讓我的 Workspace、目標、打卡及設定有穩定的私人身分。
2. 作為使用者，我想在登入後看見我的 Workspace，讓我能區分進行中、暫停、完成及放棄的目標。
3. 作為使用者，我想在首頁選擇 Keep Fit，讓我從清楚的健康目標類別開始。
4. 作為使用者，我想在 Keep Fit 中選擇 Running，讓我能建立跑步承諾。
5. 作為使用者，我想看見其他運動方式標為即將推出，讓我知道 Keep Fit 可在未來擴展而不誤以為目前可用。
6. 作為使用者，我想與 Gemini Flash 對話並提供跑步背景，讓計畫符合我的現況。
7. 作為使用者，我想填寫年齡區間、近四週的運動習慣、可跑日子、每次可用時間、期望能力及限制，讓計畫有足夠依據。
8. 作為使用者，我不想被要求提供體重、身形相片或精確住址，讓我能在不過度透露個人資料下開始規劃。
9. 作為有健康疑慮的使用者，我想在安全篩查出現警示時被建議諮詢專業人士，讓 App 不會把不安全的運動建議當成承諾。
10. 作為沒有健康警示的初學者，我想收到保守的跑走交替起步建議，讓我可循序漸進地開始。
11. 作為使用者，我想先檢視及修改 Gemini 提出的計畫草案，讓我不會被聊天中的隨口回答綁定。
12. 作為使用者，我想只有在按下「我承諾這個計畫」後才正式啟動目標，讓承諾是明確的選擇。
13. 作為承諾中的使用者，我想在建立時看見週期與達標率，例如八週完成百分之八十跑步日，讓完成的標準事先清楚。
14. 作為使用者，我想同時只保有一個進行中的 Running 目標，讓我不會用新目標逃避舊承諾。
15. 作為使用者，我想不能直接刪除已建立目標，讓我的承諾與結果都有可回顧的紀錄。
16. 作為使用者，我想以完成、放棄或暫停處理目標，讓每個目標都有清楚的結局。
17. 作為使用者，我想在放棄時填寫原因並將目標歸檔，讓我能日後理解中斷的原因。
18. 作為使用者，我想在暫停時填寫原因與恢復日期，讓暫停不是無限期逃避目標的方式。
19. 作為使用者，我想暫停最長三十天，到期後被要求恢復、再延長或放棄，讓目標不會悄悄消失。
20. 作為使用者，我想修改未來每週跑步日、時長或難度，但必須填寫原因，讓計畫可配合生活變動而不失去承諾感。
21. 作為使用者，我想修改從下一週生效並保留版本歷史，讓我不能在當天臨時改規則掩蓋缺席。
22. 作為使用者，我想計畫只指定星期幾，不要求固定開跑時間，讓我可在跑步日中自行安排時間。
23. 作為使用者，我想在跑步日先上傳第一張相片，讓我開始當天的自我打卡。
24. 作為使用者，我想在第一張相片後至少等十五分鐘才能上傳第二張，讓雙相片紀錄代表一段持續投入。
25. 作為使用者，我想兩張相片都必須在同一曆日內，讓每天的完成紀錄不會跨日混淆。
26. 作為使用者，我想在 23:45 後不能開始新的打卡，讓系統能嚴格保留第二張相片的十五分鐘期限。
27. 作為使用者，我想知道相片只是自我打卡紀錄，不會由 App 判斷我是否真的在跑步，讓規則透明而不造成錯誤指控。
28. 作為使用者，我想每次相片上傳後都收到一則正向、簡短的鼓勵，讓打卡有即時回饋。
29. 作為使用者，我想在第二張相片成功後看見當天跑步已完成，讓我得到明確的完成感。
30. 作為重視隱私的使用者，我想在首次啟用相片鼓勵前被告知相片會傳送給 Gemini，並明確同意，讓我能選擇是否啟用影像分析。
31. 作為使用者，我想關閉相片鼓勵仍可完成打卡，讓影像分析不會成為運動承諾的門檻。
32. 作為使用者，我不想收到對外貌、年齡、性別、體型、健康、情緒或其他入鏡者的評語，讓鼓勵保持安全及尊重。
33. 作為使用者，我想在跑步日 10:00 收到今日承諾提醒，讓我有時間安排運動。
34. 作為使用者，我想在 20:00 收到最後一次直接且嚴肅的提醒，讓我在當天結束前仍能回應承諾。
35. 作為使用者，我想在午夜未完成時被標記為缺席，讓系統如實記錄結果。
36. 作為缺席的使用者，我想在翌日看到補登、跳過並填原因或重新安排的選項，讓我能面對而不是忽略一次缺席。
37. 作為使用者，我想拒絕推播權限後仍可承諾，但清楚知道將不會收到提醒，讓授權保持由我決定。
38. 作為經常旅行的使用者，我想所有跑步日與午夜截止依帳戶主時區計算，讓手機自動變更時區不會意外改變結果。
39. 作為使用者，我想在 Workspace 的日曆及時間軸回顧完成、缺席、暫停、放棄和原因，讓我能看見長期模式。
40. 作為使用者，我想原始相片在九十天後自動刪除，讓打卡紀錄不會無限保存敏感影像。
41. 作為使用者，我想刪除個別相片但保留文字狀態紀錄，讓我可控管影像隱私而不改寫目標歷史。
42. 作為使用者，我想刪除整個帳戶時有三十天撤銷期，期滿後刪除個人資料、相片與目標紀錄，讓隱私權優先於日常的不可刪除規則。
43. 作為使用者，我想在 Gemini 無法回應時仍成功儲存相片及完成打卡，讓外部 AI 故障不會令我失去已履行的承諾。
44. 作為使用者，我想在 AI 失敗時收到預設鼓勵，讓回饋不中斷且不必重新上傳相片。
45. 作為使用者，我想知道只有我能看見 Workspace 和跑步相片，讓私人承諾不會變成社交壓力。
46. 作為開發者，我想讓 Gemini、推播、相片儲存、帳戶與時間來源都可替換，讓核心承諾規則可在本機、測試與正式服務間一致運作。
47. 作為開發者，我想由單一工作流判定打卡、缺席與目標狀態，讓 UI 和外部服務不會各自實作衝突的規則。

## Implementation Decisions

- App 名稱為 **Go Go Goal**，介面以繁體中文為預設語言。
- V1 將既有的通用規劃流程收斂為私人帳戶、Workspace、Keep Fit 與 Running。通用目標建立、任務匯出及多類別規劃不再是主要使用流程。
- Workspace 的目標狀態至少包含草案、進行中、暫停、完成及放棄；完成與放棄的目標均為歸檔資料，且保留原因與狀態變更時間軸。
- Running 目標包含主時區、每週跑步日、每次建議時長、週期、達標率、承諾時間、版本歷史及每日跑步紀錄。每日紀錄包含預定日期、完成／缺席／跳過狀態、兩張相片的時間戳、鼓勵結果及原因。
- 跑步計畫的建立分成資料收集、安全篩查、草案生成與明確承諾四步。安全警示時不可建立由 App 自行給出的跑步訓練處方。
- 計畫修改必須帶原因，並產生下一週生效的新版本；舊版本只讀保留。每人同時最多一個進行中的 Running 目標。
- 每日打卡以帳戶主時區的曆日為準。第一張相片時間必須不晚於 23:45；第二張必須與第一張相隔至少 15 分鐘並在相同曆日。符合規則才將該日標示為完成。
- 系統依主時區安排 10:00 提醒、20:00 最後提醒及午夜缺席結算。推播權限被拒絕時，狀態結算仍照常，僅不發送裝置通知。
- 午夜缺席後，翌日的補救流程必須記錄使用者的選擇及理由，不能悄悄覆寫原始缺席事件。
- 目標週期結束時，由確定性規則以已完成跑步日與預定跑步日計算達標率。達標才可完成；未達標只能延長、建立下一週調整或放棄歸檔。
- 相片打卡與相片鼓勵是分離的流程。完成打卡只依時間與儲存成功判定；AI 視覺分析只在使用者已同意時執行，失敗時使用預設正向文案且不得回滾打卡。
- Gemini 服務只可產生草案、鼓勵和提醒文字；不可更改目標狀態、打卡結果、通知安排、相片保留期限或任何規則。相片回應須以正向、簡短的運動鼓勵為限，並過濾敏感特徵推論。
- 原始相片的保存期限為 90 天。刪除個別相片不改變日常完成文字紀錄。帳戶刪除會進入 30 天可撤銷期，之後移除可識別資料；產品統計資料僅可保留不可回推個人的聚合值。
- 外部能力以可替換介面處理：帳戶／資料儲存、媒體儲存、通知排程、Gemini 規劃與視覺鼓勵、時鐘與時區。不得把外部 SDK 的結果直接視為領域規則。
- 唯一主要高階 seam 為 `RunningCommitmentWorkflow`。它接收主時區、目前時間、目標、每日打卡操作和使用者處理決定，輸出打卡是否合法、下一個狀態、需要安排的提醒、日曆紀錄與可顯示的結果。UI 僅透過此工作流進行承諾操作。
- V1 的 Workspace 與相片皆為使用者私有，不提供分享、好友關係、排行榜或公開動態。

## Testing Decisions

- 好的測試只驗證使用者或外部系統可觀察的結果：可否承諾、可否完成打卡、狀態是否正確、提醒是否安排、資料是否保留或刪除；不驗證 UI 內部 state、hook 呼叫順序或第三方 SDK 實作細節。
- 主要且最高的測試 seam 是 `RunningCommitmentWorkflow`。以可控制的時鐘、主時區、記憶體儲存、通知排程器、媒體儲存及 Gemini stub 測試完整承諾生命週期。
- 工作流測試必須覆蓋：草案不建立承諾、明確承諾才啟動目標、同時第二個 Running 目標被拒絕、修改在下一週才生效、暫停最長 30 天及到期處理、完成／放棄歸檔。
- 打卡測試必須覆蓋：第一張相片、未滿 15 分鐘的第二張被拒絕、跨日第二張被拒絕、23:45 後不能開始、符合規則完成、相片分析未同意時跳過、Gemini 失敗時以預設鼓勵完成。
- 排程測試必須覆蓋：主時區中的 10:00 與 20:00 通知、午夜缺席、拒絕推播時仍結算缺席、時區更改後以帳戶主時區而非裝置自動時區計算。
- 目標成果測試必須覆蓋：達標率計算、達標完成、未達標延長／調整／放棄，以及補救流程保留原始缺席紀錄。
- 儲存與資料生命週期測試必須覆蓋：重開後還原 Workspace、90 天相片清理但保留文字紀錄、個別相片刪除、帳戶刪除的 30 天撤銷與最終清除。
- 以互動測試覆蓋可見路徑：登入、選擇 Keep Fit／Running、生成並承諾草案、完成雙相片打卡、查看鼓勵及完成狀態、缺席後處理、檢視 Workspace 歷史與設定。測試依使用者可見文字、可存取標籤及操作互動，不依賴視圖階層。
- 現有程式沒有測試 prior art；本規格建立後，工作流測試與外部能力的契約測試將成為後續測試慣例。

## Out of Scope

- Keep Fit 的健身、游泳、單車、健走、瑜伽或其他運動方式。
- 閱讀、學習、飲食、睡眠、專案工作等非 Keep Fit 的目標類別。
- 好友、群組、公開排行榜、照片分享、社群動態、內容檢舉與競爭功能。
- 利用相片驗證使用者是否真的跑步，或對外貌、身分、健康、情緒作推論。
- 穿戴裝置、GPS 軌跡、心率或其他外部健康資料整合。
- 週報、月報、進階趨勢洞察及更複雜的教練自動調整。
- 完整多語言、無障礙深化、離線同步衝突解決及多裝置即時同步。
- 將既有系統日曆的行程讀入、修改或刪除；日曆只作為 Go Go Goal 完成／缺席紀錄的展示目的。

## Further Notes

- 目前程式已具備 React Native／Expo、TypeScript、本機儲存與系統日曆整合的原型基礎，但缺少本規格的帳戶、通知、媒體、目標生命週期與 Gemini 整合，實作時應以新工作流取代分散的畫面規則。
- 正式串接 Gemini Flash 時，API 金鑰不得放在行動 App；應經由受控後端服務並套用速率限制、影像同意紀錄、錯誤回退與觀測性。
- App 不得把跑步計畫描述為醫療意見。安全篩查和模型文案應持續保守，並為高風險答案提供求助專業人士的路徑。
- V1 成功與否以三個訊號評估：使用者是否願意建立正式承諾、嚴肅提醒是否促成對缺席的回應、雙相片與日曆紀錄是否提升持續性；不以功能數量或社交互動作為核心指標。
