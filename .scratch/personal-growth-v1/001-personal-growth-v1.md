## Problem Statement

使用者知道自己想成長，卻通常只停留在「學一門語言」、「多讀書」、「提升專注力」等模糊願望。若直接把幾個選項拼成一段自由文字交給 Gemini，計畫容易變得泛泛而談、忽略實際時間，或一次安排太多不同方向。使用者需要一條和現有「生命之輪 → 健康（身心） → 運動 → 跑步」一致、但適合學習與習慣建立的流程：先選擇成長方向，再提供目標、程度、可用時間與偏好，預覽一份可以修改、可以跟住做的計畫。

## Solution

在 Workspace 的生命之輪新增可進入的「個人成長」入口。個人成長第一版提供以下項目：

- 學習新技能
- 語言學習
- 閱讀與知識
- 思維與心態
- 專注與時間管理
- 創意與表達
- 自我探索與反思
- 建立自律與習慣

使用者可以選一個主要方向，並選最多兩個支援方向；若選了超過三個，畫面要求先排序或縮小本輪範圍，避免 Gemini 產生失焦計畫。使用者填寫的所有選項會被保留在結構化 `PersonalGrowthSubmission`，再由後端白名單清理後送給 Gemini。Gemini 只回傳結構化的里程碑、任務、時間、完成條件及可行性警示，不能自行補上使用者沒有提供的事實。

流程沿用跑步 onboarding 的核心節奏，但不把跑步的健康篩查、雙相片打卡或運動術語帶入個人成長：

1. 選擇成長方向（主要方向＋支援方向）。
2. 描述想達成的結果與目前程度。
3. 設定週期、可投入時間、可安排的星期與時間段。
4. 選擇學習方式、偏好、限制及容易中斷的情境。
5. 確認資料、產生 Gemini 草案、檢視及修改。

使用者確認草案後，才建立 Personal Growth Goal。這一階段先停在「計畫草案／確認」流程，不做 App 日曆畫面、通知或手機系統日曆同步；之後再以獨立階段加入。

## User Stories

1. 作為使用者，我想從生命之輪進入「個人成長」，讓我知道這是和跑步並列的目標類別。
2. 作為使用者，我想看見每個個人成長項目的簡短例子，讓我可以快速選擇最接近自己的方向。
3. 作為使用者，我想選一個主要成長方向，讓計畫有清楚的中心。
4. 作為使用者，我想加入最多兩個支援方向，讓計畫能反映真實需要但不會失焦。
5. 作為使用者，我想在選太多方向時重新排序或縮小範圍，讓我先完成一個可行的週期。
6. 作為使用者，我想自行輸入「完成」的定義，讓 AI 不會替我決定成功代表甚麼。
7. 作為使用者，我想選擇目前程度，讓任務從我的起點開始。
8. 作為使用者，我想補充已經維持中的習慣或已有資源，讓計畫不要重複我已經會做的事。
9. 作為使用者，我想選擇 4、8 或 12 週週期，或輸入目標日期，讓計畫符合我的時間範圍。
10. 作為使用者，我想輸入每週可投入的總時間，讓計畫不會超出我的生活容量。
11. 作為使用者，我想選擇可安排的星期及時段，讓任務可以落在我真的有空的時間。
12. 作為使用者，我想選擇閱讀、影片、練習、作品或混合模式，讓任務符合我的學習方式。
13. 作為使用者，我想輸入語言、工具、資源或環境限制，讓計畫不會要求我沒有的條件。
14. 作為使用者，我想指出容易中斷的原因，讓計畫有較輕鬆的替代版本。
15. 作為使用者，我想選擇教練語氣，讓提醒可以平靜、直接而不羞辱我。
16. 作為使用者，我想在送出前看見即將交給 Gemini 的摘要，讓我知道哪些資料會被使用。
17. 作為使用者，我想在 Gemini 生成期間看到明確的 loading，讓我知道計畫仍在處理中。
18. 作為使用者，我想在 Gemini 失敗時仍取得安全的基本計畫，讓一次服務故障不會丟失我的輸入。
19. 作為使用者，我想看到計畫的總結、里程碑、每週節奏和每項任務，讓我可以判斷是否適合自己。
20. 作為使用者，我想看到每項任務的日期、時段、預計分鐘、做法及完成條件，讓我可以直接執行。
21. 作為使用者，我想要求計畫「更輕鬆」、「更有挑戰」或「調整日子」，讓我可以在承諾前修正草案。
22. 作為使用者，我想直接編輯任務文字、日期、時間和時長，讓計畫保持我的主控權。
23. 作為使用者，我想在修改造成時間衝突時得到警示及候選時段，而不是系統自動改掉我的選擇。
24. 作為使用者，我想先確認計畫再開始，讓未同意的 AI 建議不會變成正式目標。
25. 作為使用者，我想在確認後建立個人成長目標，讓計畫可以保存並在之後繼續查看。
26. 作為使用者，我想重開 App 後保留方向、答案和草案，讓我不用重新填寫。
27. 作為使用者，我想在未確認前離開並稍後繼續，讓草案不會被迫提交。
28. 作為使用者，我想在確認後看到目前計畫內容，讓我知道下一步要做甚麼。
29. 作為使用者，我不想 AI 推測我的身分、心理診斷、健康狀況或能力，讓我的資料只用於我要求的規劃。
30. 作為開發者，我想讓個人成長使用獨立的計畫合約，讓現有 Running 五步流程和安全規則保持不變。
31. 作為開發者，我想用可替換的規劃服務介面包裝 Gemini，讓測試和日後更換模型不需要改寫畫面。

## Implementation Decisions

- 導覽路徑為「生命之輪 → 個人成長 → 成長方向 → 個人成長 onboarding → 計畫草案 → 個人成長目標」。現有「生命之輪 → 健康（身心） → 運動 → 跑步」及其五步流程維持原樣。
- 個人成長項目先採用上述八個固定項目，每項都有繁體中文名稱、說明和例子。保留「其他」自由文字欄位，但只有在使用者主動輸入後才送出。
- 方向選擇採「一個主要＋最多兩個支援」模型。第一個被選方向不應悄悄成為主要方向；畫面提供拖曳或上移／下移排序，並在產生前顯示目前排序。
- 以新的 `PersonalGrowthSubmission` 表達個人成長輸入，至少包含：分類與項目、主要／支援方向、希望結果、成功定義、目前程度、現有習慣與資源、週期或目標日期、每週分鐘上限、可安排星期、每星期日時段、偏好媒介、偏好語氣、阻礙、不可安排條件及同意送往 Gemini 的狀態。欄位可以是空值；空值代表未知，不代表 Gemini 可以猜測。
- 個人成長資料使用獨立的 `PersonalGrowthPlanDraft`、`PersonalGrowthGoal` 與 `PersonalGrowthTask` 合約。不要把個人成長任務硬塞進 `RunningPlanDraft`、`RunningGoal`、跑步相片打卡或跑步 session type；這樣可以保護現有 Running workflow。
- `Account` 先以向後兼容的可選欄位保存個人成長草案及已確認目標。讀取舊帳戶時不建立虛假的個人成長目標；只有已存在的個人成長資料才做欄位正規化。
- 設一個高階 `PersonalGrowthWorkflow` seam，負責驗證提交資料、建立安全 fallback、保存草案、接受計畫修訂及承諾目標。任務狀態、回顧、通知及日曆整合留待後續階段；UI 不直接拼 prompt 或改寫目標生命週期。
- AI 透過可替換的 planning service 呼叫。請求種類分開為 `personal-growth-plan` 和 `personal-growth-revision`，不改動現有 `initial-coaching-plan` 或 `running-plan` 合約。
- 後端 sanitize layer 只允許 personal-growth schema 中的欄位與長度，移除未知欄位、截斷過長文字、拒絕錯誤分類及拒絕未支援的任務類型。任何私人帳戶識別資料、相片、日曆內容及不必要的自由文字都不送給 Gemini。
- Gemini system instruction 要求：只使用結構化提交資料；不可捏造課程、證照、工具或使用者背景；不可作醫療、心理、法律或財務專業判斷；輸出繁體中文；任務要小而具體；每項任務要有完成條件與較輕鬆替代方案；當期限和時間容量不一致時標示 `ADJUSTED` 並提出取捨，不得偷偷超過上限。
- Gemini 回傳獨立的結構化計畫：計畫標題、摘要、週期、可行性、里程碑、每週 focus、任務列表、每項任務的日期／開始時段／時長／指示／完成條件／替代方案／原因，以及計畫級限制提醒。任務日期與時段由 App 驗證，不能只信任模型文字。
- 驗證器至少檢查：任務日期落在週期內、開始／結束時間格式正確、任務不重疊、每週總分鐘不超過提交上限、任務只落在可安排時段、里程碑日期有序、每個任務有完成條件、所有週次均有內容、不得出現未知 task type。驗證失敗時保留使用者輸入並使用 fallback 或要求重新生成。
- Fallback 使用確定性模板，依主要方向產生少量「了解／練習／輸出／回顧」任務，不宣稱 AI 個人化，也不會超過使用者的時間上限。Fallback 和 Gemini 計畫都必須能在草案畫面編輯。
- 草案檢視沿用現有「先看計畫、再承諾」原則，但使用 generic `PlanReview` 介面承載個人成長內容。可接受、開始得更輕鬆、增加挑戰、調整日子、逐項編輯和重新生成；只有「承諾並開始」才建立正式 Personal Growth Goal。
- 個人成長目標生命週期為 `DRAFT → COMMITTED → ACTIVE → PAUSED／COMPLETED／ABANDONED`。任務狀態至少有 `PLANNED／IN_PROGRESS／COMPLETED／SKIPPED／RESCHEDULED`。完成與放棄均保留事件及原因，不能用刪除掩蓋歷史。
- 第一階段不建立 App 日曆、手機系統日曆事件或通知；計畫中的日期／時段只作為草案內容，供使用者檢視及修改。
- Gemini prompt 必須以結構化 JSON 傳送，而非把所有答案直接串成未標記的長句。建議 prompt 內容分成「使用者目標」「可用容量」「偏好與限制」「輸出要求」四段，便於審查、測試和日後更換模型。
- 個人成長計畫的內容以「下一個可執行行動」為中心，不要求連續打卡、不使用羞辱或懲罰語言、不承諾一定結果。若使用者輸入涉及危機、疾病或專業治療，顯示適當的界線提示，不由 Gemini 提供處方。

## Testing Decisions

- 好的測試驗證使用者可觀察的計畫與狀態，不測試 React hooks 的呼叫順序、元件內部 state 或 Gemini SDK 實作細節。
- 以 `PersonalGrowthWorkflow` 作為最高主要 seam，使用確定性的 mock planning service 測試：方向排序、輸入驗證、fallback、草案儲存、計畫修訂及承諾。
- 以既有 `InitialCoachingWorkflow`、`RunningCommitmentWorkflow` 測試作為 prior art；新增測試必須證明 Running 的五步 onboarding、安全 gate、雙相片打卡及既有資料仍完全通過。
- 後端 contract tests 覆蓋：personal-growth request sanitize、未知欄位移除、過長文字截斷、合法／非法分類、prompt 只含允許資料、結構化回覆解析、任務不合規時拒絕及 Gemini 失敗時 fallback。
- 計畫驗證測試覆蓋：時間容量、可用星期、時段衝突、任務重疊、期限不足、里程碑順序、空任務、未知 task type 及保留使用者編輯值。
- 儲存行為測試覆蓋：個人成長草案與目標重開後仍存在、舊帳戶沒有個人成長欄位時安全載入、損毀的成長資料不影響 Running 資料。
- UI／互動測試覆蓋：生命之輪進入個人成長、八個項目顯示、選擇及排序、問卷暫存、送出前摘要、loading、fallback、草案編輯、未承諾返回、確認後保存及重開還原。
- Expo web smoke／typecheck 只驗證規劃流程可編譯與可操作；原生日曆權限及事件建立不在本階段驗證範圍。

## Out of Scope

- 修改或重寫現有健康（身心）→ 運動 → 跑步五步 onboarding。
- 其他生命之輪類別（財富／財務、事業／職業、人際關係、休閒娛樂、生活環境、人生意義／貢獻）的可用規劃流程；它們仍顯示「即將推出」。
- App 內日曆、通知及手機系統日曆同步；這些功能改放到後續階段。
- Gemini 讀取使用者既有系統日曆、郵件、檔案、相片或第三方學習平台。
- 系統日曆的雙向同步、匯入事件、修改外部事件、跨裝置同步及雲端帳戶同步。
- 自動購買課程、尋找付費資源、替使用者聯絡他人或執行外部服務操作。
- 以心理診斷、醫療、法律、財務或學業評分取代使用者及專業人士的判斷。
- 社群、排行榜、連續天數壓力、公開分享、教練人工介入及付費訂閱。
- 讓 Gemini 在背景無限期自動改寫未確認的計畫。

## Further Notes

- 第一階段只做「個人成長項目＋問卷＋結構化 fallback／Gemini 草案＋草案確認」。日曆、通知及同步另立 Phase 2／Phase 3，避免一次改動太多。
- 最重要的新 seam 是 `PersonalGrowthWorkflow` 加上可替換的 `PlanningService`；`CalendarGateway` 暫時不加入第一階段。
- 這份規格使用現有產品詞彙：Workspace、生命之輪、草案、承諾、fallback、Gemini。它不要求現在把所有 Running 型別重構成一個大型 union。
- GitHub issue 尚未發布：本機沒有可用的 `gh` CLI／issue tracker connector。文件已按 `ready-for-agent` 保存；有 GitHub connector 或 `gh` 授權後，可用同一標題及內容建立 issue。
